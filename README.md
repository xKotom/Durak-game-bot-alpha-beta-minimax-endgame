## 2. Что делает бот

Бот играет в **подкидной дурак 1-на-1** с колодой 36 карт (ранги 6..14, 4 масти). Управляющий модуль `MTable` (его менять нельзя) дёргает методы:

| Метод | Когда | Что возвращает |
|---|---|---|
| `GetName()` | старт | имя |
| `GetCount()` | каждый ход | размер моей руки |
| `SetTrump(card)` | старт партии | — (запоминаем козырь) |
| `AddToHand(card)` | при доборе/взятии | — (кладём карту в руку) |
| `LayCards()` | моя атака | список карт на стол |
| `Defend(table)` | моя защита | true (отбился) / false (беру) |
| `AddCards(table, def)` | подкидывание | true (подкинул) / false (нечего) |
| `OnEndRound(table, ok)` | конец раунда | — (обновляем учёт) |

## 4. Стратегия — четыре идеи

### А) Экономия козырей в дебюте

В `Defend` есть три «правила отказа»:
- **Rule 1**: coloda > 6 + 2+ козырей по плану → беру.
- **Rule 2**: coloda > 4 + старший козырь (J+) в плане → беру.
- **Rule 3**: coloda > 6 + 1-card атака на картинку (J+) козырем → беру.

И safety net поверх (override):
- `planTrumpCount == 0` — защита бесплатная.
- `coloda ≤ 4` — эндгейм, поздно экономить.
- `countIfTake ≥ 11` — взять слишком много, рука раздуется.

### Б) Подкид парами/тройками не-козырей

`LayCards` кладёт **одну** карту ранга 6..10 у которого ≥2 копий в руке. Остальные карты того же ранга идут потом через `AddCards` (правило подкидывания: можно класть только ранги уже на столе). Не-козыри потому что козырные пары опп бьёт более старшими козырями (плохой обмен). Картинки бережём — они хорошие отбивающие карты.

### В) Stage 4 эндгейм-минимакс

Когда `coloda == 0`, скрытой информации нет: я знаю руку оппа точно (`ComputeOppExactHand`).

Запускаем **alpha-beta minimax** глубины `Stage4MinimaxDepth = 6` полу-раундов:
1. `MinimaxStage4PickAttack` перебирает все ходы из `EnumerateAttackMoves` (multi-card combos сначала по убыванию размера, потом одиночки — move ordering для cutoff'ов).
2. Для каждого хода:
   - Если опп не может побить (точная проверка через bipartite matching `CanOppDefendAll`) → берёт стол → защитник растёт, роли НЕ меняются.
   - Иначе отбивается жадно (`GreedyDefense`) → обе руки уменьшаются, роли МЕНЯЮТСЯ (negamax-инверсия).
3. Рекурсивно `MinimaxStage4` симулирует дальше до `depth=0`. Eval = `defHand.Count - attHand.Count`.
4. Выбираем ход с максимальной оценкой.

Bipartite matching (DFS-augmenting / алгоритм Куна) — точная проверка «может ли опп отбить ВСЕ атаки разными картами». Жадный вариант (как у типоласта) изредка ошибается на сложных раскладах с козырями.

### Г) Точный учёт состояния

`OnEndRound` — самый «бухгалтерский» метод. От его корректности зависит всё:
- Эндгейм-минимакс по неверной `oppExact` → выберет проигрышную атаку.
- Неверная `player2_cards` → `AddCards` подкинет больше чем у оппа в руке → MTable бросит исключение → партия проиграна.

Что отслеживается:
- `dump` — пополняется при успешной защите (все пары стола → бито).
- `oppKnown` — пополняется когда защитник берёт; уменьшается при `AddToHand`.
- `coloda` — уменьшается на симулированный добор (атакующий до 6 первым, потом защитник).
- `hand` — точная по `AddToHand` от MTable.

**Закон сохранения:** `36 = hand + opp + coloda + dump + table` всегда.

## 5. Разбор методов (по группам)

### 5.1 API для MTable
- `GetName()` / `GetCount()` — отдают имя / размер руки.
- `SetTrump(NewTrump)` — старт партии: запоминает козырь, сбрасывает учёт.
- `AddToHand(card)` — добавляет в `hand`, убирает из `oppKnown`.
- `LayCards()` / `Defend()` / `AddCards()` / `OnEndRound()` — главные методы (см. ниже).

### 5.2 Базовые утилиты
- `SameCard(a, b)` / `RemoveCardFromList(list, c)` / `ListContainsCard(list, c)` — линейный поиск по списку карт.
- `CountTableCards(table)` / `CountUnbeaten(table)` — счётчики стола.
- `SubtractCards(hand, remove)` — копия списка минус удалённые карты (для минимакса).

### 5.3 Учёт состояния
- `UpdateOppCount(table)` — пересчитывает `player2_cards` через закон сохранения.
- `UpdateStage()` — обновляет `stage` по `coloda`.
- `ComputeOppExactHand(table)` — точная рука оппа (только в stage 4).

### 5.4 Утилиты атаки/защиты
- `CanOppBeat(atk, oppCards)` — может ли опп побить одну атаку?
- `GenerateCombinations(group, size, ...)` — backtracking C(n, k).
- `FindMinBeatIn(target, h)` — минимальная карта в `h` бьющая `target`.
- `BuildDefencePlan(table)` — план отбивки, `null` если нечем.

### 5.5 Эндгейм-минимакс
- `CanOppDefendAll(subset, oppCards)` — точное bipartite matching через DFS-augmenting (алгоритм Куна).
- `TryAugmentDefence(...)` — поиск увеличивающей цепочки.
- `EnumerateAttackMoves(handCards)` — все ходы атакующего с move ordering (multi-card combos сначала по убыванию размера, потом одиночки по возрастанию ранга).
- `GreedyDefense(attack, defHand)` — жадная защита (модель типоласта).
- `MinimaxStage4(attHand, defHand, depth, alpha, beta)` — рекурсивный alpha-beta. Take-ветка не меняет перспективу, defend-ветка инвертирует через negamax.
- `MinimaxStage4PickAttack(...)` — top-level: выбирает лучшую атаку.

### 5.6 Главные методы

**`LayCards()`** — атака (по приоритету):
1. Stage 4 + рука ≥ 1 → `MinimaxStage4PickAttack`.
2. Иначе рука < 3 → выбрасываем максимум.
3. Иначе → ранг 6..10 с ≥2 не-козырей (1 карту, остальные через AddCards), либо минимальный не-козырь, либо минимум из руки.

**`Defend(table)`** — защита:
1. `BuildDefencePlan` → `null` → беру.
2. Считаем «цену» (трампы в плане, старший трамп, потраченные трампы, размер руки если возьму).
3. Применяем Rule 1, 2, 3 → `doDefend = false`.
4. Safety net (бесплатная защита / эндгейм / перебор) → `doDefend = true`.
5. Применяем план: `np.SetUp(beat, trump.Suit)` для каждой пары.

**`AddCards(table, OpponentDefenced)`** — подкид:
1. `maxAdd = min(6 - table.Count, player2_cards - unbeaten)`.
2. Кандидаты: карты с рангом уже на столе.
3. Сортировка: stage 4 — непобиваемые первыми; иначе не-козыри по возрастанию.
4. Лимит по стадии и исходу (1..4).
5. Фильтр `AllowedToThrow` (не сливаем козыри/картинки рано).

**`AllowedToThrow(c)`** — фильтр по стадии:
- Рука < 3 / stage 4 → всё.
- Stage 1 → не-козыри ≤ 10. Stage 2 → козырь < 10, не-козырь < 12. Stage 3 → козырь ≤ 12, не-козыри все.

**`OnEndRound(table, IsDefenceSuccesful)`** — учёт:
1. `dump`/`oppKnown`: защита удалась → пары в бито; иначе → защитник забирает.
2. Имитация добора: атакующий до 6, потом защитник до 6, оба ограничены `coloda`.

## 7. FAQ

**Q: Почему depth 7 хуже depth 6?**
A: Глубже симуляция → накапливается ошибка от упрощённого defender-модели (`GreedyDefense` ≈ типоласт, не точный bipartite). Глубже неточность важнее.

**Q: Почему в `MinimaxStage4` есть ветка «defender takes» с тем же `alpha/beta` (не negamax)?**
A: По правилам дурака если защитник берёт, атакующий продолжает атаковать в следующем раунде. Перспектива не меняется → знаки не инвертируются. Negamax только в defend-ветке (там роли реально меняются).

**Q: Почему в minimax не моделируется AddCards (подкидывание)?**
A: Упрощение для скорости. После initial attack → defend в реальной игре идёт цикл «атакующий подкидывает / защитник отбивает» пока кто-то не остановится. Симулируется только initial attack, AddCards считается «сыгранным внутри» одного полу-раунда. На практике для эндгейма этого хватает.

**Q: А что мешает сделать минимакс ещё глубже / в stage 3?**
A: Stage 3 = неполная информация (часть карт в колоде, часть у оппа). Пробовали determinized minimax (усреднение по 100+ вариантам руки оппа) — регрессирует, потому что усреднение даёт «среднюю» атаку вместо оптимальной. Реально помог бы только настоящий MCTS, но это намного сложнее.

**Q: Почему bipartite matching строго лучше жадного?**
A: Жадный для каждой атаки берёт минимальный беат локально. Иногда минимальный беат на атаку A «отъедает» карту нужную для атаки B — глобально матчинг возможен через перепривязку, но жадный его не находит. Bipartite (DFS-augmenting) ищет совершенное паросочетание точно. На малых руках разница редкая, но в эндгейме (где каждая карта на счету) важная.

## 8. Слабые места

- **Greedy-модель защитника в minimax** — реальный типоласт следует rules 1-3 (иногда берёт когда мог отбить). Симуляция этого не учитывает → eval смещён.
- **`OnEndRound` симуляция добора** — зависит от точной последовательности `AddToHand` от MTable. Edge case → `coloda` дрейфует → `player2_cards` врёт.
- **Stage 1-3 без минимакса** — там работают только эвристики (rules + AllowedToThrow). Возможна тонкая регрессия в миттельшпиле.
- **Move ordering статический** — multi-card сначала по размеру. Динамическое (best-first из transposition table) могло бы дать ещё cutoff'ов.
